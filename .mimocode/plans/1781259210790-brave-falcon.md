# Bookmark Helper 前端架构审查与优化方案

## 一、项目概述

WXT 浏览器扩展，使用 React 19 + TypeScript + Orama 向量数据库 + HuggingFace Transformers.js（gte-small）实现本地语义书签搜索。

### 当前文件结构
```
├── core/                      # 核心业务逻辑
│   ├── BookmarkIndexer.ts     # 书签索引模块（Orama DB）
│   ├── ModelManager.ts        # 嵌入模型管理
│   ├── SearchEngine.ts        # 混合搜索 + 重排序
│   ├── SyncManager.ts         # 书签变化监听
│   ├── TextPreprocessor.ts    # 文本预处理
│   └── utils.ts               # 工具函数
├── entrypoints/               # WXT 入口
│   ├── background.ts          # Service Worker
│   ├── content.ts             # Content Script
│   └── popup/                 # 弹出窗口 UI
│       ├── App.tsx
│       ├── main.tsx
│       ├── index.html
│       ├── style.css
│       └── components/
│           ├── SearchInput.tsx
│           ├── ResultList.tsx
│           ├── StatusBar.tsx
│           └── SettingsPanel.tsx
├── types/index.ts             # 类型定义
└── wxt.config.ts              # WXT 配置
```

## 二、架构问题分析

### 🔴 高优先级问题

#### 1. 单例模式滥用 — core 层耦合严重
**现状**: `ModelManager`、`BookmarkIndexer`、`SearchEngine`、`SyncManager` 全部使用硬编码单例模式（`static getInstance()`），类之间通过 `getInstance()` 直接互相引用。
- `SearchEngine` → 直接调用 `ModelManager.getInstance()` 和 `BookmarkIndexer.getInstance()`
- `SyncManager` → 直接调用 `BookmarkIndexer.getInstance()`
- `BookmarkIndexer` → 直接调用 `ModelManager.getInstance()`
- `background.ts` → 同时创建所有实例

**问题**: 
- 无法在测试中替换依赖（无法 mock）
- 模块间耦合为星型拓扑，修改任意一个都可能影响其他
- Service Worker 唤醒时单例重建逻辑不可靠

**优化方案**: 引入依赖注入容器（DI Container）或模块初始化器

#### 2. background.ts 职责过重
**现状**: `background.ts` 既是消息路由层，又承担了索引初始化、元数据增强、状态广播等多项职责（148行），包含业务逻辑（`handleMetadataExtracted`）和基础设施逻辑（Port 管理）。

**优化方案**: 将 background.ts 拆分为：
- `message-handler.ts` — 消息路由
- `metadata-enhancer.ts` — 元数据增强逻辑
- `port-manager.ts` — Port 连接管理
- `background.ts` — 只做初始化编排

#### 3. 无错误边界和容错机制
**现状**: 
- 搜索失败直接抛出到 popup，无重试逻辑
- 模型加载失败无降级方案（整个插件不可用）
- `BookmarkIndexer.buildIndex()` 无取消机制（用户无法中断）
- `SyncManager.triggerRebuild()` 失败后无恢复策略

**优化方案**: 添加错误边界、重试策略和优雅降级

### 🟡 中优先级问题

#### 4. UI 层架构不清晰
**现状**: `App.tsx` 是一个 257 行的"上帝组件"，集中管理：
- 搜索状态（query, results, isLoading）
- 索引状态（indexStatus）
- 设置面板（isSettingsOpen, config）
- 主题切换逻辑
- 最近书签展示逻辑
- 所有业务回调（handleSearch, handleRebuildIndex, handleOpenBookmark...）

**优化方案**: 
- 使用 `useReducer` 或状态管理库拆分状态
- 将配置管理、主题切换等逻辑抽取为自定义 hooks
- App.tsx 只做组件编排

#### 5. CSS 全局样式污染
**现状**: `style.css`（516行）全部使用全局类名，无 CSS Modules 或命名空间隔离。在浏览器扩展中容易与其他页面样式冲突。

**优化方案**: 
- 迁移到 CSS Modules（WXT 原生支持）
- 或使用 Tailwind CSS
- 或为所有类名添加 `bh-` 前缀

#### 6. Content Script 每次导航都发送消息
**现状**: `content.ts` 在所有页面（`*://*/*`）加载时立即提取元数据并发送给 background，无论该 URL 是否有书签。大量无效消息增加 background 负担。

**优化方案**: 
- 先查询 `chrome.bookmarks.search({ url })` 再决定是否发送
- 或在 background 端做快速过滤

#### 7. 类型系统不够严格
**现状**: 
- `types/index.ts` 的 `Message` 接口定义了消息类型，但 `background.ts` 的 `MessageRequest` 类型是独立定义的，没有复用
- `SettingsPanel.tsx` 使用 `@/types` 路径别名，其他文件用 `../../types`
- 多处使用 `as any` / `as unknown as Record<string, unknown>` 类型断言

#### 8. 缺少统一的消息通信层
**现状**: popup ↔ background 通信混合使用：
- `chrome.runtime.sendMessage`（一次性请求）
- `chrome.runtime.connect`（持久 Port 连接）
- 消息类型分散在 `background.ts`、`App.tsx` 中硬编码

**优化方案**: 创建统一的消息通信模块，定义完整的请求/响应类型映射

### 🟢 低优先级问题

#### 9. 缺少测试
**现状**: 无任何测试文件。核心模块（SearchEngine 的 rerank 逻辑、TextPreprocessor 的 URL 解析、detectQueryType 等）都是纯函数，非常适合单元测试。

#### 10. 缺少代码规范工具
**无 ESLint 和 Prettier 配置。依赖于 README 描述和代码约定。**

#### 11. buildIndex 未传递 onProgress 回调
**现状**: `SyncManager.triggerRebuild()` 调用 `buildIndex()` 时没有传入 `onProgress` 回调，导致批量重建时 popup 无法收到进度更新。

#### 12. ModelManager 使用远程模型但 .gitignore 忽略本地模型
**现状**: `ModelManager.ts` 设置了 `env.allowLocalModels = false; env.allowRemoteModels = true`，而 `package.json` 中有 `download-model` 脚本下载本地模型到 `public/models/`。`.gitignore` 忽略了 `public/models/`。两者策略不一致。

## 三、优化方案

### 用户选择：渐进式重构 + 全工具链 + 远程模型统一

**Phase 1: 基础设施（无功能变更）**
1. 添加 ESLint + Prettier 配置
2. 添加 Vitest 测试框架
3. 添加 TypeScript strict mode
4. 统一类型定义，消除 `as any`
5. 消息通信模块化 (`core/message-protocol.ts`)

**Phase 2: 核心层重构**
6. 依赖注入重构 core 模块（移除硬编码单例）
7. 拆分 `background.ts` 的职责
8. 添加错误边界和重试策略
9. 优化 Content Script 的触发条件
10. 移除 `download-model` 脚本和 `.gitignore` 中的 `public/models/`，ModelManager 确认只使用远程模型

**Phase 3: UI 层重构**
11. CSS → CSS Modules
12. 拆分 `App.tsx` 为更小的组件
13. 抽取自定义 hooks

**Phase 4: 测试**
14. 为纯函数（TextPreprocessor, SearchEngine.rerank, utils）添加 Vitest 单元测试

## 五、验证方式

每个 Phase 完成后：
1. **类型检查**: `pnpm compile` 确保 TypeScript 无报错
2. **Lint 检查**: `pnpm lint` 确保代码规范（Phase 1 后可用）
3. **构建验证**: `pnpm build` 确保生产构建成功
4. **功能验证**: `pnpm dev` 加载扩展，测试搜索、设置、重建索引功能
5. **测试**: `pnpm test` 运行单元测试（Phase 4）

## 六、风险评估

- Phase 2 单例重构是最大风险点，需确保 Service Worker 唤醒后依赖注入正确初始化
- Phase 3 CSS Modules 迁移需确保类名映射正确
- 每个 Phase 独立验证后再进入下一 Phase
